## 🔐 Authentication

When authentication is enabled, include a Bearer token in the `Authorization` header:

```bash
curl -X POST http://localhost:9002/api/v1/embed \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <your-jwt-token>" \
  -d '{"text": "Hello, world!"}'
```

### Getting a token

**Endpoint:** `POST /api/v1/auth/login`

**Request body:**

```json
{
  "username": "admin",
  "password": "Secure@Passw0rd!"
}
```

**Response:**

```json
{
  "token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 86400
}
```

| Field | Type | Description |
|------|------|------|
| `token` | string | JWT access token |
| `token_type` | string | Token type (always `Bearer`) |
| `expires_in` | integer | Seconds until token expiry (the server-returned actual value, not 0); determined by default by `[auth] token_expiration_hours` (default 24 → 86400s), overridable via `token_expiration_seconds` |

> **ℹ️ Note**: the seconds until token expiry are determined by `[auth] token_expiration_hours` (default 24 hours); only debugging/E2E may override via `[auth] token_expiration_seconds`. `src/api/auth.rs` backfills garrison's actual expiry seconds into `expires_in` verbatim.

### Refreshing a token

**Endpoint:** `POST /api/v1/auth/refresh`

**Request body:**

```json
{
  "refresh_token": "eyJhbGciOiJIUzI1NiIs..."
}
```

**Response:** same format as the login response, returning a new `token` and `expires_in`.

### Logout

**Endpoint:** `POST /api/v1/auth/logout`

**Headers:** `Authorization: Bearer <your-jwt-token>`

**Response:** a successful logout returns an empty body; the current token is revoked.

### Current user

**Endpoint:** `GET /api/v1/auth/me`

**Headers:** `Authorization: Bearer <your-jwt-token>`

**Response:**

```json
{
  "username": "admin",
  "roles": ["admin"]
}
```

### Embeddings

#### Generating an embedding

Generates a vector embedding for a single text.

**Endpoint:** `POST /api/v1/embed`

| Parameter | Type | Required | Description |
|------|------|------|------|
| `text` | string | ✅ | Text to embed |
| `normalize` | boolean | ❌ | Whether to normalize the vector (default: false) |

**Request example:**

```bash
curl -X POST http://localhost:9002/api/v1/embed \
  -H "Content-Type: application/json" \
  -d '{
    "text": "The quick brown fox jumps over the lazy dog",
    "normalize": true
  }'
```

**Response:**

```json
{
  "embedding": [0.123, 0.456, 0.789, ...],
  "dimension": 1024,
  "processing_time_ms": 15.5
}
```

| Field | Type | Description |
|------|------|------|
| `embedding` | array | Embedding vector array |
| `dimension` | integer | Vector dimension |
| `processing_time_ms` | number | Processing time (milliseconds) |

### 🌐 OpenAI-compatible API

VecBoost provides an OpenAI-compatible embeddings endpoint supporting the `dimensions` parameter for Matryoshka dimensionality reduction.

#### Generating embeddings (OpenAI-compatible)

**Endpoint:** `POST /v1/embeddings`

| Parameter | Type | Required | Description |
|------|------|------|------|
| `input` | string \| array | ✅ | Text or text array to embed (up to 2048 items) |
| `model` | string | ✅ | Model ID (supports the `text-embedding-ada-002` mapping) |
| `encoding_format` | string | ❌ | Encoding format (`float`, `base64`) |
| `dimensions` | integer | ❌ | Output dimension (supports 1-1024; BGE-M3 max 1024) |
| `user` | string | ❌ | User identifier |

**Request example (single text):**

```bash
curl -X POST http://localhost:9002/v1/embeddings \
  -H "Content-Type: application/json" \
  -d '{
    "input": "Hello, world!",
    "model": "text-embedding-ada-002",
    "dimensions": 256
  }'
```

**Request example (batch):**

```bash
curl -X POST http://localhost:9002/v1/embeddings \
  -H "Content-Type: application/json" \
  -d '{
    "input": ["文本1", "文本2", "文本3"],
    "model": "text-embedding-ada-002",
    "dimensions": 512
  }'
```

**Response:**

```json
{
  "object": "list",
  "data": [
    {
      "object": "embedding",
      "embedding": [0.123, 0.456, 0.789, ...],
      "index": 0
    },
    {
      "object": "embedding",
      "embedding": [0.111, 0.222, 0.333, ...],
      "index": 1
    }
  ],
  "model": "text-embedding-ada-002",
  "usage": {
    "prompt_tokens": 10,
    "total_tokens": 10
  }
}
```

#### 🧊 Matryoshka dimensionality reduction

The `dimensions` parameter controls the output vector dimension for smaller, faster embeddings:

| Requested `dimensions` | Actual returned dimension | Use case |
|-------------------|-------------|----------|
| `256` | 256 | Maximum speed, minimal storage |
| `512` | 512 | Balanced performance |
| `1024` | 1024 | Maximum quality (default) |

**Dimension limits:**
- Minimum: 1
- Maximum: the model's maximum dimension (1024 for BGE-M3)
- Without a `dimensions` parameter, the full dimension is returned

**Automatic re-normalization after truncation**:

After performing the Matryoshka truncation (`truncate_vector`), VecBoost immediately calls `normalize_l2` to re-run L2 normalization on the truncated vector. This is necessary — truncation breaks the original vector's unit length, and without re-normalization:
- Cosine similarity would fall outside the `[-1, 1]` range
- Dot products would no longer be equivalent to cosine similarity
- Similarity comparisons against the original 1024-dim vector would be distorted

> **💡 Tip**: this normalization applies to every Matryoshka-capable entry point (HTTP `/v1/embeddings`, `/api/v1/embed*`, gRPC `vecboost.embed*`, MCP, CLI). If a request explicitly sets `normalize: false` while passing `dimensions`, re-normalization still runs after truncation to keep semantics correct.

**Error response (dimension over limit):**

```json
{
  "error": {
    "message": "dimensions 2048 exceeds model maximum 1024",
    "type": "invalid_request_error"
  }
}
```

### Similarity

#### Computing similarity

Computes similarity between two texts (cosine by default, switchable via `metric`). The server embeds both texts automatically before computing.

**Endpoint:** `POST /api/v1/similarity`

| Parameter | Type | Required | Description |
|------|------|------|------|
| `source` | string | ✅ | Source text |
| `target` | string | ✅ | Target text |
| `metric` | string | ❌ | Similarity metric: `cosine` (default) / `euclidean` / `dot_product` / `manhattan`. Distance metrics convert to similarity via `1/(1+d)` |

**Request example:**

```bash
curl -X POST http://localhost:9002/api/v1/similarity \
  -H "Content-Type: application/json" \
  -d '{
    "source": "机器学习是人工智能的子领域",
    "target": "深度学习基于神经网络"
  }'
```

**Response:**

```json
{
  "score": 0.8765
}
```

| Field | Type | Description |
|------|------|------|
| `score` | number | Similarity score. `cosine` (default) ranges [-1, 1]; `dot_product` is unbounded; `euclidean` / `manhattan` convert via `1/(1+d)` into (0, 1] |

1-vs-N retrieval: given a query text, returns the Top-K candidates ranked by descending similarity.

**Endpoint:** `POST /api/v1/search`

| Parameter | Type | Required | Description |
|------|------|------|------|
| `query` | string | ✅ | Query text |
| `texts` | string[] | ✅ | Candidate text list (≤100) |

```json
{
  "results": [

    { "text": "今天的午餐是面条", "score": 0.32, "index": 1 }

}
```

### Decision answering (Decisions)

Answers a set of choice / score / noul questions for a given decision context `state` (Laya decision pipeline, `onnx` feature).

**Endpoint:** `POST /api/v1/decisions`

> **⚠️ Either-or task**: available only under `[model] task = "decision"`; with `task = "embedding"` (default), calls return `400` (`UnsupportedTask`, prompting a model/endpoint switch).

**Request fields:**

| Parameter | Type | Required | Description |
|------|------|------|------|
| `state` | any JSON | ✅ | Decision context (free-form JSON with model-agreed semantics); string leaves containing control characters are rejected with 400 |
| `questions` | array | ✅ | Question array (1–32), answered in array order |
| `questions[].name` | string | ✅ | Question name (non-empty, unique; answers echo it back) |
| `questions[].qtype` | string | ✅ | `choice` / `score` / `noul` |
| `questions[].instructions` | string | ✅ | Question instruction |
| `questions[].options` | array | Conditional | For choice: required, non-empty option set (≤64); score/noul must not carry it |

**Request example (one of each type):**

```bash
curl -X POST http://localhost:9002/api/v1/decisions \
  -H "Content-Type: application/json" \
  -d '{
    "state": {"topic": "vacation"},
    "questions": [
      {"name": "destination", "qtype": "choice", "instructions": "pick one", "options": ["beach", "mountain"]},
      {"name": "budget", "qtype": "score", "instructions": "rate 1-5"},
      {"name": "confident", "qtype": "noul", "instructions": "state your p(true)"}
    ]
  }'
```

**Response:**

```json
{
  "answers": [
    {
      "question": "destination",
      "answer": {"type": "choice", "index": 1, "option": "mountain", "probabilities": {"beach": 0.25, "mountain": 0.75}}
    },
    {
      "question": "budget",
      "answer": {"type": "score", "expected": 3.5, "distribution": {"3": 0.5, "4": 0.5}}
    },
    {
      "question": "confident",
      "answer": {"type": "noul", "p_true": 0.9}
    }
  ],
  "processing_time_ms": 12
}
```

**Response structure per qtype (`answer.type` internally tagged):**

| qtype | answer fields | Description |
|-------|-------------|------|
| `choice` | `index` / `option` / `probabilities` | Matched option index and original text + full normalized probability table |
| `score` | `expected` / `distribution` | Expected grade Σ(i·p_i) + full grade distribution |
| `noul` | `p_true` | P(true) from the two-option softmax |

### Translation (Translate)

Translates text between configured language pairs (Marian/opus-mt seq2seq, `onnx` feature, greedy decoding).

**Endpoint:** `POST /api/v1/translate`

> **⚠️ Configuration semantics**: language pairs come from `[[translation.pairs]]` in the `[translation]` section (built eagerly at startup); with zero configuration the endpoint stays registered and every request returns `400` (`translate-not-configured`).
>
> **Behavior**: when the target language hits the Chinese/Japanese/Korean code families (`zh`/`zho`/`cmn`/`yue`, `ja`/`jpn`, `ko`/`kor`), the translation goes through CJK half-width punctuation normalization (`,;:?!` → full-width; digits flanked by digits (thousands/time context) and periods excluded — see USER_GUIDE "Translation punctuation normalization").

**Request fields:**

| Parameter | Type | Required | Description |
|------|------|------|------|
| `text` | string | ✅ | Text to translate (≤10,000 characters, counted as characters; control characters are rejected with 400) |
| `source_language` | string | ❌ | Source language code (lowercase ISO 639-1); absent or `null` = auto-detection (unreliable → 400 `translate-detect-failed`; the result backfills `detected_source_language`) |
| `target_language` | string | ✅ | Target language code (lowercase ISO 639-1; must differ from the source) |

**Request example:**

```bash
curl -X POST http://localhost:9002/api/v1/translate   -H "Content-Type: application/json"   -d '{"text": "Hello, my dog is cute", "source_language": "en", "target_language": "zh"}'
```

**Response:**

```json
{
  "translation": "你好，我的狗好可爱",
  "source_language": "en",
  "target_language": "zh",
  "detected_source_language": null,
  "processing_time_ms": 258
}
```

With auto-detection, `source_language` is `null` and `detected_source_language` carries the detected code (e.g. `"en"`) — the null key appears explicitly, never omitted.

**400 error-code semantics:**

| Message key | Trigger |
|--------|----------|
| `translate-empty-text` | text is empty |
| `translate-too-long` | text exceeds 10,000 characters (counted as characters) |
| `translate-not-configured` | zero language pairs configured |
| `translate-unsupported-pair` | `(source,target)` missed the routing table (message includes the requested pair and the full configured set) |
| `translate-unsupported` | the routed engine does not support the translation task |
| `translate-detect-failed` | auto-detection unreliable (digits-only/too-short text) |
| `translate-too-many-source-tokens` | source token count exceeds the pair's `max_source_tokens` (message includes the actual value and cap) |

### Transcription (Transcribe)

Transcribes 16kHz mono f32 speech samples into text (Qwen3-ASR: silero VAD segmentation → per-segment decoding → in-order concatenation; `transcribe` feature, blocking inference isolated via spawn_blocking).

**Endpoint:** `POST /api/v1/transcribe`

> **⚠️ Configuration semantics**: the engine comes from the `[transcribe]` section (`enabled`/`models_dir`/`vad_threshold`, built eagerly at startup); with `enabled=false` or the `transcribe` feature disabled, the endpoint stays registered and every request returns `400` (`transcribe-not-configured`).
>
> **Behavior**: the client is responsible for WAV decoding (16kHz mono f32 `[-1,1]`, ≤2 hours); the domain layer validates non-empty/all-finite/length caps. When VAD segmentation is empty (all silence), `segments` is empty and `text` is empty (an explicit empty response, not an error). Concurrent requests serialize through a permits=1 semaphore; queueing returns `503`.
>
> **CLI subcommand available**: `transcribe` registers `cli=true`, passing JSON via `--req` (e.g. `--req '{"wav_path":"audio.wav"}'`; the CLI input structure is `TranscribeWavRequest { wav_path }`, reading wav → samples → the domain request); the domain contract is the samples array (HTTP/gRPC pass it directly).

**Request fields:**

| Parameter | Type | Required | Description |
|------|------|------|------|
| `samples` | array<number> | ✅ | 16kHz mono f32 samples (`[-1,1]`; non-empty/all-finite/≤2h, violations 400) |

**Request example:**

```bash
curl -X POST http://localhost:9002/api/v1/transcribe   -H "Content-Type: application/json"   -d '{"samples": [0.01, -0.02, 0.0]}'
```

**Response:**

```json
{
  "text": "你好世界",
  "segments": [
    {
      "start_sec": 0.0,
      "end_sec": 5.12,
      "text": "你好世界"
    }
  ],
  "processing_time_ms": 4210
}
```

`text` always equals the in-order concatenation of each segment's `text` (a domain-layer invariant); `processing_time_ms` is server wall-clock.

**400 error-code semantics:**

| Message key | Trigger |
|--------|----------|
| `transcribe-not-configured` | `[transcribe] enabled=false` or the `transcribe` feature is not enabled |

### Language detection (Detect)

Detects the natural language of text (whatlang n-gram statistics, µs-level pure CPU, no model dependency; also the single source of truth behind translation auto-detection).

**Endpoint:** `POST /api/v1/detect`

**Request fields:**

| Parameter | Type | Required | Description |
|------|------|------|------|
| `text` | string | ✅ | Text to inspect (≤10,000 characters, counted as characters) |
| `allow` | array | ❌ | Language-code allowlist (narrows candidates; empty = no narrowing; invalid codes 400) |

**Request example:**

```bash
curl -X POST http://localhost:9002/api/v1/detect   -H "Content-Type: application/json"   -d '{"text": "The quick brown fox jumps over the lazy dog near the riverbank every morning."}'
```

**Response:**

```json
{
  "language": "en",
  "script": "Latin",
  "confidence": 1.0,
  "is_reliable": true,
  "processing_time_ms": 0
}
```

Undetectable (no detection signal / digits-only / symbols-only) returns **200** + `language: null` + `is_reliable: false` (explicitly expressed; silent success or a fabricated language is forbidden).

### Language-code contract and translation limitations

**Language-code contract** (shared by translation and detection):

- Lowercase ISO 639-1 codes first (e.g. `en`/`zh`/`ja`); whatlang variants without a 639-1 equivalent fall back to 639-3 codes (e.g. `epo` for Esperanto)
- Lowercase enforced end to end (`^[a-z]{2,3}$`); uppercase (`"EN"`) gets an explicit 400; no case normalization
- Not BCP-47 (no region subtags)

**Translation limitations:**

- Marian (2019 architecture) quality ceiling; no BLEU metric promised
- Default 512-token window (`max_source_tokens`/`max_new_tokens` configurable, hard cap 1024); over-limit is **rejected explicitly, not truncated**
- Single-text requests; no batch endpoint
- Greedy decoding (no-cache branch; the Xenova merged-graph cache branch has an export defect, see the `src/engine/onnx_translate.rs` module docs)

**Endpoint:** `GET /api/v1/model/current`

**Response:**

## 🔌 gRPC API

### Service definition

Since v0.2.0, VecBoost's gRPC interface no longer depends on hand-written `.proto` files; it is generated automatically by the `sdforge` framework from the single-source handler definitions via the `#[forge(grpc_method = "...")]` macro (one single source per domain under `src/api/`: embedding / rerank / decisions / translate / detect). Clients call the corresponding methods through sdforge's unified `SdForgeService/Call` RPC:

- Request payloads are JSON-serialized domain types passed via `CallRequest.data`
- Response payloads are JSON-serialized domain types returned via `CallResponse.data`
- The service name is fixed as `SdForgeService`; method names are the `vecboost.*` identifiers in the table below

```rust
// src/api/embedding.rs
#[cfg(feature = "grpc")]
#[forge(
    name = "vecboost_embed",
    version = "v1",
    grpc_method = "vecboost.embed",
    description = "Generate embedding vector for input text"
)]
pub async fn grpc_embed(req: EmbedRequest) -> Result<EmbedResponse, ApiError> {
    embed_handler(req).await
}
```

> **💡 Tip**: no `proto/` directory or `tonic-build`-generated client stubs are needed. All gRPC methods are registered via the `#[forge(grpc_method = "...")]` macro in the per-domain single sources under `src/api/` (embedding / rerank / decisions / translate / detect) — 17 `vecboost.*` methods in total.

### gRPC service configuration

The gRPC service starts via `sdforge::grpc::build_server_with_config`; settings live in the `[server]` section:

| Setting | Type | Default | Description |
|--------|------|--------|------|
| `grpc_max_connections` | `usize` | `1000` | Maximum concurrent connections |
| `grpc_timeout_seconds` | `u64` | `30` | Request timeout (seconds) |
| `grpc_require_auth` | `bool` | `true` | Whether to enforce JWT auth (BearerAuth) |
| `grpc_allowed_roots` | `Vec<String>` | none (must be configured explicitly) | Allowed-root directories for file-embedding path validation; unconfigured or empty makes `/embed/file` always return 400 prompting for the setting (**no cwd fallback**) |

With `grpc_require_auth = true`, all of the following must hold:
- `[auth] enabled = true`
- The `auth` feature is compiled in
- The `VECBOOST_JWT_SECRET` environment variable is set (≥32 chars) or `auth.jwt_secret` is non-empty

Otherwise the service fails to start. In addition, gRPC enables the `LimiteronAdapter` rate limiter by default (default 100 burst / 10 req/s).

### Message type definitions

> **ℹ️ Note**: the structures below are the Rust domain types defined in `src/domain/` (serde serialization). gRPC requests/responses travel as JSON byte streams through sdforge `CallRequest.data` / `CallResponse.data`; the HTTP interface likewise submits a JSON body. Field names are `snake_case`.

#### Embedding request/response

```rust
// request
struct EmbedRequest {
    text: String,
    normalize: Option<bool>,
}

// response
struct EmbedResponse {
    embedding: Vec<f32>,
    dimension: usize,
    processing_time_ms: u128,
    information_retention_rate: Option<f32>,  // filled on Matryoshka truncation
}

// batch request
struct BatchEmbedRequest {
    texts: Vec<String>,
    mode: Option<AggregationMode>,
    normalize: Option<bool>,
}

// batch response

    embeddings: Vec<BatchEmbeddingResult>,  // each with text_preview + embedding
```

### SDK usage examples

> **ℹ️ Note**: since v0.2.0, VecBoost does not publish its own `.proto` or generated clients. Clients use the `SdForgeService` stub generated from sdforge's unified proto (`sdforge/proto/sdforge.v1.proto`, package `sdforge.v1`), calling specific methods through the `Call` RPC with a method name (e.g. `vecboost.embed`) and a JSON payload. The examples below demonstrate this calling pattern.

#### grpcurl (command-line debugging)

```bash
# 1. Query available service methods (including vecboost.*)
grpcurl -plaintext localhost:50051 sdforge.v1.SdForgeService/GetInfo

# 2. Call vecboost.embed (method field carries the method name, data field the JSON)
grpcurl -plaintext -d '{
  "method": "vecboost.embed",
  "data": "{\"text\":\"Hello, world!\",\"normalize\":true}"
}' localhost:50051 sdforge.v1.SdForgeService/Call
```

#### Python

```python
import json
import grpc
import sdforge_v1_pb2
import sdforge_v1_pb2_grpc

# Connect to the gRPC service (SdForgeService generated from the sdforge.v1 proto)
channel = grpc.insecure_channel('localhost:50051')
stub = sdforge_v1_pb2_grpc.SdForgeServiceStub(channel)

# Single embedding request: method=vecboost.embed, data=JSON-serialized EmbedRequest
call_req = sdforge_v1_pb2.CallRequest(
    method="vecboost.embed",
    data=json.dumps({"text": "Hello, world!", "normalize": True}),
)
call_resp = stub.Call(call_req)
if not call_resp.success:
    raise RuntimeError(f"vecboost.embed failed: {call_resp.error}")

embed_resp = json.loads(call_resp.data)
print(f"Embedding dimension: {embed_resp['dimension']}")
print(f"Processing time: {embed_resp['processing_time_ms']:.2f}ms")

# Batch embedding request: method=vecboost.embed_batch
batch_req = sdforge_v1_pb2.CallRequest(
    method="vecboost.embed_batch",
    data=json.dumps({"texts": ["文档1", "文档2", "文档3"], "normalize": True}),
)
batch_resp = stub.Call(batch_req)
batch_data = json.loads(batch_resp.data)
print(f"Processed {batch_data['total_count']} embeddings")
```

#### Go

```go
import (
    "context"
    "encoding/json"
    "fmt"
    "log"
    "time"

    "google.golang.org/grpc"
    "google.golang.org/grpc/credentials/insecure"
    pb "sdforge/v1" // generated from sdforge/proto/sdforge.v1.proto
)

func main() {
    // Connect to the sdforge gRPC service (SdForgeService/Call)
    conn, err := grpc.Dial("localhost:50051",
        grpc.WithTransportCredentials(insecure.NewCredentials()))
    if err != nil {
        log.Fatalf("Failed to connect: %v", err)
    }
    defer conn.Close()

    client := pb.NewSdForgeServiceClient(conn)

    // Build an EmbedRequest, JSON-serialized as CallRequest.data
    payload, _ := json.Marshal(map[string]any{
        "text":      "Hello, world!",
        "normalize": true,
    })

    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()

    resp, err := client.Call(ctx, &pb.CallRequest{
        Method: "vecboost.embed",
        Data:   string(payload),
    })
    if err != nil {
        log.Fatalf("Call failed: %v", err)
    }
    if !resp.Success {
        log.Fatalf("vecboost.embed failed: %s", resp.Error)
    }

    var embed struct {
        Dimension          int64   `json:"dimension"`
        ProcessingTimeMs   float64 `json:"processing_time_ms"`
    }
    if err := json.Unmarshal([]byte(resp.Data), &embed); err != nil {
        log.Fatalf("decode response: %v", err)
    }
    fmt.Printf("Dimension: %d, Time: %.2fms\n",
        embed.Dimension, embed.ProcessingTimeMs)
}
```

> **📝 Generating client stubs**: Python uses `python -m grpc_tools.protoc -I. --python_out=. --grpc_python_out=. sdforge/proto/sdforge.v1.proto`; Go uses `protoc --go_out=. --go-grpc_out=. sdforge/proto/sdforge.v1.proto`. Once generated, any `vecboost.*` method can be called — VecBoost itself need not publish a proto.

By default (without the `auth` feature) there are 18: `embed_text` / `embed_batch` / `compute_similarity` / `search` / `file_embed` / `rerank` / `rerank_batch` / `decisions` / `translate` / `detect` / `transcribe` / `list_models` / `get_current_model` / `get_model_info` / `model_switch` / `model_unload` / `health` / `openai_embed`. With the `auth` feature enabled, 4 additional auth tools register (`src/api/auth.rs`, gated by `#[cfg(all(feature = "auth", feature = "http"))]`): `login` / `logout` / `refresh_token` / `get_current_user`. Tools are generated by the `#[forge(tool_name = ...)]` macro from the same handlers as REST/gRPC, with inputs/outputs reusing the same-named domain types from the message-type definitions above (JSON format); the `decisions` tool succeeds only under `[model] task = "decision"` (otherwise 400 Unsupported task); the `translate` tool requires `[translation]` pairs configured (otherwise 400 `translate-not-configured`); the `detect` tool has no configuration dependency.

## 💻 CLI tools

The `cli` feature provides the clap command-line tool (generated by sdforge from the same handlers as HTTP/gRPC). `--config <path>` / `--config=<path>` also work in this mode: `strip_config_args()` walks all arguments before clap parsing and strips the option, so it may appear before or after the subcommand (a dangling `--config` without a path exits with code 2):

```bash
cargo run --features cli -- embed --req '{"text":"Hello, world!"}'                # single-text embedding
cargo run --features cli -- embed_batch --req '{"texts":["文本1","文本2"]}'       # batch embedding
cargo run --features cli -- compute_similarity --req '{"source":"机器学习","target":"人工智能"}'  # similarity
cargo run --features cli -- search --req '{"query":"查询文本","texts":["候选1","候选2"]}'     # semantic search
cargo run --features cli -- rerank --req '{"query":"什么是机器学习","documents":["文档1","文档2"]}'     # rerank
cargo run --features cli -- decisions --req '{"state":{"topic":"vacation"},"questions":[{"name":"confident","qtype":"noul","instructions":"state your p(true)"}]}'  # decision answering (nested request via --req JSON; available under task=decision)
cargo run --features cli -- translate --req '{"text":"Hello, my dog is cute","source_language":"en","target_language":"zh"}'  # translation ([translation] pairs configured; source_language absent = auto-detection)
cargo run --features cli -- detect --req '{"text":"The quick brown fox jumps over the lazy dog."}'  # language detection (no model dependency; optional allow allowlist field)
```

> **ℹ️ Note**: unknown subcommands print a usage hint and exit (code 2) instead of silently starting the HTTP server.

## 🚨 Error handling

### HTTP status codes

| Status | Description |
|--------|------|
| `200` | ✅ Success |
| `400` | ❌ Bad request / validation error |
| `401` | 🔒 Unauthorized (missing or invalid token) |
| `403` | 🚫 Forbidden (insufficient RBAC permissions, returned by the auth middleware) |
| `404` | 🔍 Resource/model not found |
| `422` | 🧩 Tokenization failure |
| `424` | 🔗 Model load failure / not loaded |
| `429` | ⚡ Too many requests (returned only by the auth rate-limit middleware per IP/user/API key; application-level rate limiting/queue backpressure uses `503`) |
| `500` | 💥 Internal server error (including config/DB/IO) |
| `503` | ⏸️ Service unavailable (application-level rate limiting `error-rate-limit`, queue full `error-overloaded`, inference failure `error-inference`; with Retry-After) |
| `504` | ⏳ Server-side request timeout (`error-request-timeout`, queueing/processing exceeded the SLA) |
| `507` | 🧊 Memory exhausted (GPU/CPU OOM) |

---

### Error response format

All error responses follow a unified format and support internationalization (i18n):

```json
{
  "error": "配置错误：数据库连接超时",
  "code": 500,
  "error_code": "error-config"
}
```

| Field | Type | Description |
|------|------|------|
| `error` | string | Error description (auto-translated per the current locale) |
| `code` | integer | HTTP status code |
| `error_code` | string | Fluent message key for programmatic error classification |

---

### Common error codes

| error_code (Fluent key) | HTTP status | Description | Resolution |
|--------|-------------|------|----------|
| `error-invalid-input` | 400 | Invalid request parameters | Check the request body format |
| `error-validation` | 400 | Input validation failed | Check the input content |
| `error-unsupported-task` | 400 | The current engine/model does not support this task dimension | Switch model or endpoint |
| `error-authentication` | 401 | Authentication failed / token invalid | Obtain and use a valid token |
| `error-not-found` | 404 | Resource/model not found | Check the resource name |
| `error-tokenization` | 422 | Tokenization failed | Check the input text encoding |
| `error-model-load` | 424 | Model load failure (missing dependency) | Check model files and configuration |
| `error-model-not-loaded` | 424 | Model not loaded | Load the model first |
| `error-rate-limit` | 503 | Application-level rate-limit backpressure (auth rate-limit semantics; wire is 503 not 429) | Retry with exponential backoff |
| `error-overloaded` | 503 | Priority queue full / overload backpressure (`Retry-After`) | Back off and retry |
| `error-request-timeout` | 504 | Server-side queueing/processing exceeded the SLA | Reduce batch size, retry later |
| `error-inference` | 503 | Inference failure | Check model state |
| `error-oom` | 507 | GPU/CPU memory exhausted | Reduce batch size or use CPU |
| `error-config` | 500 | Configuration error | Check the config file |
| `error-database` | 500 | Database error | Check DB connectivity and configuration |
| `error-internal` | 500 | Internal error | Contact the administrator |

> **ℹ️ Boundary**: every `error_code` in the table is generated by `VecboostError::error_code()` (`src/error.rs`) as a Fluent message key (shaped like `error-config`); the HTTP response body fills `error_code` with that value alongside the numeric `code` (HTTP status) and the localized `error` text. Two status codes do not originate from `VecboostError`: `429` comes from the auth rate-limit middleware (garrison, per IP/user/API key) and `403` from RBAC permission checks — neither has a corresponding `VecboostError` variant.

> **💡 Tip**: with authentication enabled, an `error-authentication` (401) error may also mean the token has expired.

---

### 🌐 Internationalization (i18n)

VecBoost supports bilingual (English/Chinese) error responses, built on the ICU+Fluent framework. HTTP requests switch language automatically via the `Accept-Language` header, with this priority:

| Priority | Source | Example |
|--------|------|------|
| 1 (highest) | `Accept-Language` header (request level) | `Accept-Language: zh-CN` |
| 2 | `VECBOOST_LANG` environment variable (global default) | `VECBOOST_LANG=zh` |
| 3 | `LC_ALL` / `LANG` environment variables | `LANG=zh_CN.UTF-8` |
| 4 | System locale (`sys-locale`) | Operating-system language setting |
| 5 (default) | English | `en` |

**Error message example (Chinese):**

```json
{
  "error": "验证错误：文本 index 0 长度 5000 超过限制 1024",
  "code": 400,
  "error_code": "error-validation"
}
```

**The same error in English:**

```json
{
  "error": "Validation error: text at index 0 has length 5000 exceeding limit 1024",
  "code": 400,
  "error_code": "error-validation"
}
```

> **ℹ️ Note**: the `error_code` field is a Fluent message key (e.g. `error-config`, `error-validation`) usable for programmatic error handling, unaffected by language switching. Supported languages: `en` (English), `zh` (Chinese). Unsupported languages automatically fall back to English.

## ⚡ Rate limiting

### Default limiting policy

Rate limiting is based on limiteron's native `TokenBucketLimiter`, with independent Global/Ip/User/ApiKey dimensions:

| Limit type | Requests | Time window | Use case |
|----------|--------|----------|----------|
| **Global** | 1,000 | per minute | Protects the overall service |
| **Per IP** | 100 | per minute | Guards against single-IP attacks |
| **Per user** | 200 | per minute | User-level limiting |
| **Per API key** | 500 | per minute | API-key-level limiting |

---

### Rate-limit response headers

The rate-limit middleware returns token-bucket quotas via the IETF `RateLimit-*` header family (controlled by `[rate_limit] headers_enabled`, **off by default**); note this is the `RateLimit-*` family, not `X-RateLimit-*`. When rejected (429/auth rate limiting), a `Retry-After` is also attached:

| Header | Description |
|--------|------|
| `RateLimit-Policy` | Rate-limit policy string (e.g. `100;w=60`: quota 100 + window 60 seconds) |
| `RateLimit-Limit` | Maximum requests in the window for the current limiting dimension |
| `RateLimit-Remaining` | Remaining requests in the window |
| `RateLimit-Reset` | Seconds until the window resets |

**Example:**

```
RateLimit-Policy: 100;w=60
RateLimit-Limit: 100
RateLimit-Remaining: 95
RateLimit-Reset: 43
```

---

### Exceeding the rate limit

Application-level rate limiting/queue backpressure over-limit returns `503 Service Unavailable` with `Retry-After` (**not 429**: pipeline rate limiting `error_rate_limit` and queue-full `error-overloaded` both map to 503; `429` is returned only by the auth IP/user/API-key rate-limit middleware):

```json
{
  "error": "Rate limit exceeded. Try again in 30 seconds.",
  "code": 503,
  "error_code": "error-rate-limit"
}
```

---

### Customizing rate limits

Adjust rate limits in the config file:

```toml
[rate_limit]
enabled = true
global_requests_per_minute = 2000
ip_requests_per_minute = 200
user_requests_per_minute = 500
api_key_requests_per_minute = 1000
window_secs = 60
ip_whitelist = ["127.0.0.1"]
```
