## 🚀 Quick start

For experienced users, this is the fastest way to get started:

```bash
# 1. Clone and build
git clone https://github.com/Kirky-X/vecboost.git
cd vecboost
cargo build --release

# 2. Run with default settings
./target/release/vecboost

# 3. Test the API (in a new terminal)
curl -X POST http://localhost:9002/api/v1/embed \
  -H "Content-Type: application/json" \
  -d '{"text": "Hello, VecBoost!"}'
```

**Expected output:**

```json
{
  "embedding": [0.123, 0.456, ...],
  "dimension": 1024,
  "processing_time_ms": 15.5
}
```

> **⏱️ Estimated time**: 2-5 minutes (depending on network and hardware)

### 🔨 Building from source

#### Option 1: CPU only (all platforms)

```bash
git clone https://github.com/Kirky-X/vecboost.git
cd vecboost
cargo build --release
```

#### Option 2: CUDA support (Linux)

```bash
# Set CUDA environment variables
export CUDA_HOME=/usr/local/cuda
export LD_LIBRARY_PATH=$CUDA_HOME/lib64:$LD_LIBRARY_PATH

# Build
cargo build --release --features cuda
```

#### Option 3: Metal support (macOS)

```bash
cargo build --release --features metal
```

#### Option 4: Everything

```bash
# All protocols (HTTP/gRPC/MCP/CLI)
cargo build --release --features http,grpc,mcp,cli

# All protocols + all optional capabilities (GPU/ONNX/auth/database; db requires the sqlite or postgres driver; Redis goes through distributed-redis, see the FAQ)
cargo build --release --features http,grpc,mcp,cli,cuda,onnx,auth,db,sqlite
```

> **💡 Tip**: `default = ["http", "onnx"]` — the default build includes the HTTP protocol and the ONNX Runtime primary engine. gRPC/MCP/CLI protocols must be enabled explicitly via `--features`. confers (config), inklog (logging), oxcache (cache), limiteron (rate limiting), and trait-kit (module registry) are mandatory dependencies that need no feature; `redis` is not a standalone feature (multi-replica shared state is provided by `distributed-redis`, see the FAQ).

## 🔧 Configuration

### 📄 Config file

Copy the sample config:

```bash
cp config/config.toml config/config_custom.toml
```

The global `--config <path>` (or `--config=<path>`) argument selects the config file and works for both server and CLI modes. It is stripped from all arguments by `strip_config_args()` before clap parsing, so it may appear before or after the subcommand (`vecboost --config config_custom.toml embed --req '{"text":"Hello"}'` is equivalent to `vecboost embed --req '...' --config config_custom.toml`); a dangling `--config` without a path exits with code 2. An explicit missing path fails fast with an error and exit code 2. Three presets ship: `config/config.toml` (default, secure defaults: loopback binding, GPU off), `config/config_full.toml` (a fuller example — note it contains legacy **unparsed** sections `[flow_control]` / `[cache]` (backend="redis") / `[advanced]`, and is not an exhaustive list of parsed sections), and `config/config_minimal.toml` (minimal example).

---

### 📁 Config section overview

The table below corresponds to the sections actually parsed by `VecboostConfig` (`src/config/app_config.rs`):

| Section | Description | Library / Feature |
|------|------|------------------|
| `[server]` | Bind address, port, timeout, CORS, gRPC settings | - |
| `[model]` | Model repo, device, precision, quantization, multi-model residency | - |
| `[embedding]` | Pooling, similarity metric, cache, text length caps, WAL persistence | oxcache |
| `[rerank]` | Rerank `max_documents_per_query` / `max_query_length`, exact cache `cache_enabled` (default false) / `cache_size` | - |
| `[monitoring]` | Memory limits, metric collection | prometheus |
| `[auth]` | JWT, CSRF, admin account, token lifetime | garrison (`auth`) |
| `[rate_limit]` | Multi-dimensional token-bucket rate limiting | limiteron |
| `[audit]` | Audit log | inklog |
| `[database]` | Database connection (`[database] url = "sqlite:vecboost.db"`) | dbnexus (`db`) |
| `[logging]` | Log level, console, file rotation | inklog |
| `[pipeline.worker]` | Time-window batching `batch_wait_ms` / `max_batch_size` / shutdown drain `drain_timeout_secs` | - |
| `[semantic_cache]` | Semantic cache `comparison_mode` (deprecated, kept but ineffective), `fuzzy_threshold`, `backend` (memory/redis), `redis_url` | oxcache / Redis |
| `[device]` | Hardware-aware planning `auto_plan` | - |
| `[translation]` | Translation language pairs `[[translation.pairs]]` (routing, bundle paths, token budget) | - (requires the `onnx` feature) |
| `[transcribe]` | Transcription service switch, Qwen3-ASR bundle directory, VAD threshold, session knobs (endpoint always registered; 400 `transcribe-not-configured` when disabled) | - (requires the `transcribe` feature) |

> **⚠️ Note**: the `[flow_control]` and `[cache]` TOML sections are **not parsed in the current version — edits have no effect** (legacy section names); rate limiting uses `[rate_limit]`, caching uses `[embedding]` and `[semantic_cache]`. The tuning-switch registry is in [⚡ Performance Guide](PERFORMANCE.md).

### 🔧 Main configuration options

#### Server settings

```toml
[server]
host = "0.0.0.0"    # bind address
port = 9002         # HTTP port
timeout = 30        # request timeout (seconds)
cors_enabled = false          # whether to enable CORS (off by default)
cors_allow_origins = []       # allowed cross-origin sources
```

| Parameter | Default | Description |
|------|--------|------|
| `host` | `0.0.0.0` | Bind address |
| `port` | `9002` | HTTP port |
| `timeout` | `30` | Request timeout (seconds) |
| `cors_enabled` | `false` | Whether to enable CORS |
| `cors_allow_origins` | `[]` | Allowed cross-origin source list; containing `"*"` or empty means any origin (effective only when `cors_enabled = true`) |

> **💡 Tip**: HTTP response gzip compression is always enabled — no configuration needed.

#### gRPC settings

The gRPC protocol is enabled via the `grpc` feature (`cargo build --release --features grpc`); all protocol handlers are generated by sdforge. gRPC settings live in the `[server]` section:

```toml
[server]
grpc_enabled = false              # whether to enable the gRPC service
grpc_host = "0.0.0.0"             # gRPC bind address (optional, defaults to host)
grpc_port = 50051                 # gRPC port
grpc_max_connections = 1000       # maximum concurrent connections
grpc_timeout_seconds = 30         # gRPC request timeout (seconds)
grpc_require_auth = true          # whether to enforce JWT auth
grpc_allowed_roots = ["/data"]    # file-embedding allowed roots (/embed/file requires this; 400 without it)
```

| Parameter | Default | Description |
|------|--------|------|
| `grpc_enabled` | `false` | Whether to enable the gRPC service |
| `grpc_host` | same as `host` | gRPC bind address (optional) |
| `grpc_port` | `50051` | gRPC port |
| `grpc_max_connections` | `1000` | Maximum concurrent connections |
| `grpc_timeout_seconds` | `30` | gRPC request timeout (seconds) |
| `grpc_require_auth` | `true` | Whether to enforce JWT auth (enforced by default) |
| `grpc_allowed_roots` | - (no default) | Allowed-root list for file embedding; `/embed/file` must be configured explicitly — 400 when unconfigured or empty (no cwd fallback) |

> **⚠️ Security note**: `grpc_require_auth` defaults to `true`; callers must explicitly set `grpc_require_auth = false` to disable auth. Keep it enabled in production and configure `grpc_allowed_roots` to restrict accessible paths — this setting is not optional: `/embed/file` always returns 400 when it is missing. `/model/switch`'s local-path validation has a different default (falls back to `models/` when unconfigured).

#### Model settings

```toml
[model]
model_repo = "BAAI/bge-m3"  # HuggingFace model ID
use_gpu = false             # enable GPU (requires the corresponding feature)
batch_size = 32             # batch size
expected_dimension = 1024   # embedding dimension
max_sequence_length = 8192  # maximum tokens per request
```

| Parameter | Default | Description |
|------|--------|------|
| `model_repo` | `BAAI/bge-m3` | HuggingFace model ID |
| `model_path` | - | Local model path (preferred over HF fetch when set) |
| `tokenizer_path` | - | Explicit tokenizer path override: **consumed by the onnx local-bundle branch (by engine_type) and the decision pipeline (by task="decision", engine_type not involved)** — for local bundle loads it takes precedence over root and `tokenizer/` subdirectory probing, and a configured-but-missing path errors loudly at engine load; other combinations (candle/quantized embedding, the onnx HF fetch branch, non-local directories) do not consume this field (startup warn) |
| `use_gpu` | `false` | Whether to use the GPU |
| `batch_size` | `32` | Batch size |
| `expected_dimension` | `1024` | Embedding dimension |
| `max_sequence_length` | `8192` | Maximum sequence length |

> **`task` (engine-level ModelConfig field, default `embedding`)**: the task dimension; one of
> `embedding` / `decision` / `translate` / `transcribe`. The `[model]` section supports `task`; invalid values (such as
> `"rerank"`) error loudly at config parsing. With `task = "decision"`, the EngineFactory's
> task dispatch arm loads the Laya decision pipeline (succeeds when the bundle is ready;
> a missing/incomplete bundle reports `ModelLoadError`), the `/api/v1/decisions` decision endpoint
> becomes available, and vector endpoints like `/embed` are rejected loudly with `UnsupportedTask`
> (400) — see the bundle-layout notes in the `[model]` section of
> `config/config.toml`.
> With `task = "translate"`, the dispatch arm loads the ONNX seq2seq translation engine (only
> `engine_type = "onnx"`; candle is rejected loudly), making the `/api/v1/translate` endpoint available;
> translation language pairs do not consume the `[model]` section — they live in the `[translation]` section (see
> "Translation language-pair configuration" below).
> `#[serde(default)]` guarantees zero breakage for old config files.
>
> **`engine_type` (engine-level ModelConfig field, default `onnx`)**: the inference engine
> type; one of `onnx` / `candle`. Since onnx-primary (2026-10-16) the primary inference engine is
> ONNX Runtime (the `onnx` feature ships with default; unset `None` = onnx);
> `"candle"` is the opt-in fallback backend, requiring a `--features candle` build; without it,
> the configuration errors loudly at startup. Unknown values error loudly at startup. With `task = "decision"` this
> field dispatches the decision backend (the candle-native decision head needs the `candle` feature; the Laya onnx
> bundle is onnx-format); with `task = "translate"`
> it is forced to onnx (candle has no seq2seq implementation; configuring it errors at startup).
> Decision-request token caps: per question, head+options (prompt + options) together ≤192 tokens,
> the state section ≤256 tokens (longer input is prefix-truncated); over-budget requests are rejected with 400
> (the prompt/options are not truncated — truncation would change the question's meaning). Long requests that
> pass this layer's character/byte checks may still be rejected by the token basis
> (CJK characters have higher token density). `model_sha256` validates only the decision
> bundle's main model file; tokenizer.json and laya_config.json treat the bundle directory
> permissions as the trust boundary (minimal write permissions recommended for deployment).

> **⚠️ Key-spelling note**: unknown keys in TOML config sections are **silently ignored** (TOML parsing has no
> `deny_unknown_fields`). Misspelled keys (such as `task` typed as `tsak`) do not error;
> the field silently falls back to its default. After changing config, confirm it took effect via `vecboost doctor`
> — the `config` check echoes the parsed `model.task` (e.g.
> `VecboostConfig::validate passed (model.task=embedding)`), so a misspelled `task`
> shows the fallback value `embedding`.
>
> The engine-level `vecboost::config::model::ModelConfig` (library API surface) has
> `deny_unknown_fields` enabled: when its serialized artifacts (config snapshots / persisted configs) are read
> across versions, fields added by an upgrade are **explicit deserialization errors** for older binaries rather than
> silent ignores — verify the artifact field set before downgrading.

#### Laya decision bundle acquisition

`task = "decision"` requires the Laya ONNX bundle to be ready. Besides manual download, the library API
`vecboost::utils::hf_hub::download_files` can fetch the official bundle in one call (HF direct connection only;
mirrors such as hf-mirror.com are unsupported due to the hf-hub 1.0.0 ETag limitation):

```rust
use vecboost::utils::hf_hub::{LAYA_BUNDLE_FILES, LAYA_BUNDLE_REPO, download_files};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let manifest: Vec<(String, std::path::PathBuf)> = LAYA_BUNDLE_FILES
        .iter()
        .map(|f| ((*f).to_string(), std::path::PathBuf::from(f)))
        .collect();
    let downloaded = download_files(
        LAYA_BUNDLE_REPO,
        &manifest,
        std::path::Path::new("models/laya-decision"),
    )
    .await?;
    println!("downloaded {} files", downloaded.len());
    Ok(())
}
```

- Built-in manifest constant `LAYA_BUNDLE_REPO = "receptron/laya-onnx"`, 5 files total:
  `laya.onnx`, `laya.onnx.data`, `laya_config.json`,
  `tokenizer/tokenizer.json`, `tokenizer/tokenizer_config.json`. The consistency of the built-in constants with
  the upstream files is pinned by an online integration test (red first when upstream adds/removes files):
  `HF_INTEGRATION=1 cargo test -p vecboost --test hf_hub_integration`.
- Any file download failure aggregates into one error that lists the successful and failed files with their
  respective causes (no silent partial success); remote paths containing `..` traversal, empty manifests, and invalid repo_ids are all
  rejected loudly before any network request.
- Files already in place **with byte counts matching the remote** are skipped (hf-hub local_dir downloads write
  directly to the final path and interruptions leave partial files, so the size check prevents partial files from being treated as success; when the size cannot be confirmed,
  always re-download). Manifest downloads use a dedicated HTTP client (10s connect timeout, no total timeout),
  so slow direct links downloading 1.6 GB-scale assets are not interrupted by a 300s-class total timeout.
- The ~1.6 GB `laya.onnx.data` lands under `models/` (covered by `.gitignore`),
  not in git. After downloading, set `model_path = "models/laya-decision"` to the bundle directory.

> **⚠️ Disable note**: `Mattepiu/laya-onnx` is a broken artifact with a static `[.,2]` marker dimension,
> **forbidden as a download target** — it exports the marker-gather dimension with a static shape,
> making variable-length prompts un-inferable. Use only the official `receptron/laya-onnx`.

Local bundle directory loading basis: the tokenizer is resolved by one contract shared by the embedding and decision
pipelines — in the order of `[model].tokenizer_path` (a configured-but-missing path errors loudly, no silent
fallback) → root `tokenizer.json` → `tokenizer/tokenizer.json` (all missing errors).
ONNX main-model file probing diverges per pipeline (task protocol convention): embedding (`engine_type =
"onnx"`) probes `model_quantized.onnx` → `model.onnx` → the only `*.onnx` in the directory (multiple
candidates error with a list); decision (`task = "decision"`) follows the fixed list `model.onnx` →
`model_quantized.onnx` → `laya.onnx` → `laya_int8.onnx` (fp32 main model first).

#### Candle-native decision path

`engine_type = "candle"` + `task = "decision"` runs the Rust-native decision-head forward
(ModernBERT-large backbone + decision head, **no onnxruntime shared-library dependency**), consuming
official assets of a different shape than the `engine_type = "onnx"` ort pipeline:

```toml
[model]
model_path = "models/laya-pytorch"   # PyTorch checkpoint directory (layout below)
task = "decision"
engine_type = "candle"               # opt-in fallback backend: requires a --features candle build (the default primary engine is onnx)
```

With `engine_type = "onnx"`, the same configuration consumes the ONNX bundle under
`models/laya-decision` ("Laya decision bundle acquisition" above); both paths share the same preprocessing protocol,
the three post-processings, and the temperature-calibration semantics, with `|Δlogit| ≤ 1e-4` numeric alignment pinned by an offline gate test.

The official PyTorch checkpoint is the safetensors weights of `convaiinnovations/laya`, fetched via the library API `download_files` — the following 5 files into `models/laya-pytorch/`
(HF direct connection only; mirror limitations as above):

```rust
use std::path::Path;
use vecboost::utils::hf_hub::download_files;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let files = [
        "model.safetensors",
        "rl_agent_config.json",
        "encoder/config.json",
        "tokenizer/tokenizer.json",
        "tokenizer/tokenizer_config.json",
    ];
    let manifest: Vec<(String, std::path::PathBuf)> = files
        .iter()
        .map(|f| ((*f).to_string(), std::path::PathBuf::from(f)))
        .collect();
    let downloaded = download_files(
        "convaiinnovations/laya",
        &manifest,
        Path::new("models/laya-pytorch"),
    )
    .await?;
    println!("downloaded {} files", downloaded.len());
    Ok(())
}
```

Equivalently, pre-fetch with huggingface-cli:
`huggingface-cli download convaiinnovations/laya model.safetensors rl_agent_config.json encoder/config.json tokenizer/tokenizer.json tokenizer/tokenizer_config.json --local-dir models/laya-pytorch`.

- `model.safetensors` (842,609,210 bytes ≈ 0.84 GB, F16 storage, auto-upcast to F32 at
  runtime): ModernBERT-large backbone (`encoder/` key prefix) + decision head (
  `head/`/`scorer/`/`act_head/`/`type_emb` keys).
- `models/` is covered by `.gitignore`; checkpoints are not committed.
- The `tokenizer/` layout matches the bundle's resolution contract (root `tokenizer.json` →
  `tokenizer/tokenizer.json`).
- `rl_agent_config.json` is a decision-head hyperparameter reference (head_layers=2, head_max_len=192,
  bucketed calibration temperatures `temperature_by_options`); its bucket key format (e.g. `choice:3-5`)
  differs from the bundle-side `laya_config.json` integer-cardinality keys and is currently not parsed —
  the candle path's temperature calibration keeps the status quo of "missing `laya_config.json` falls back to 1.2".
- The alignment gate test (candle-native forward vs the onnx `DecisionPipeline` on the same questions,
  `|Δlogit| ≤ 1e-4`) requires that checkpoint and `ORT_DYLIB_PATH` to be in place,
  and the whole file SKIPs when missing (probes centralized in `tests/common/mod.rs`).

### Translation language-pair configuration

Translation is driven by the `[[translation.pairs]]` array tables of the `[translation]` section (orthogonal to the
`[model]` task section): each pair is built eagerly at startup (the EngineFactory task=translate
dispatch arm, `onnx` feature); any missing bundle **fails fast at startup** (the error includes the language-pair
identifier); with zero configuration the service still pre-builds unconditionally, the `/api/v1/translate` endpoint stays registered, and requests
are rejected loudly with `400` (`translate-not-configured`).

```toml
[translation]

[[translation.pairs]]
source_language = "en"
target_language = "zh"
model_path = "models/opus-mt-en-zh"
# tokenizer_path = "models/opus-mt-en-zh/tokenizer.json"   # optional explicit override
# max_source_tokens = 512    # optional (default 512, hard cap 1024)
# max_new_tokens = 512       # optional (default 512, hard cap 1024)

[[translation.pairs]]
source_language = "en"
target_language = "es"
model_path = "models/opus-mt-en-es"
```

| Field | Required | Description |
|------|------|------|
| `source_language` / `target_language` | ✅ | Lowercase ISO 639-1 codes (639-3 where no equivalent), `^[a-z]{2,3}$`; uppercase is rejected loudly, no case normalization; duplicate `(source,target)` pairs error at startup |
| `model_path` | ✅ | Translation bundle directory (contract in the next section) |
| `tokenizer_path` | ❌ | Explicit tokenizer override (defaults to the bundle's `tokenizer.json`) |
| `max_source_tokens` / `max_new_tokens` | ❌ | Token budget (default 512/512, hard cap 1024; over-limit errors at startup) |

The pair cap is 16 (one resident bundle per pair, a memory-budget defense). Requests route exactly by
`(source_language, target_language)`: a miss returns `400`
`translate-unsupported-pair` (the message includes the requested pair and the full configured set); when `source_language`
is absent, whatlang auto-detection runs (the same implementation as `/api/v1/detect`); unreliable detection (digits-only/
too-short text) returns `400` `translate-detect-failed`; reliable results backfill
`detected_source_language`.

**Translation punctuation normalization**: when the target language hits the Chinese/Japanese/Korean code families (`zh`/`zho`/`cmn`/`yue`, `ja`/
`jpn`, `ko`/`kor`), the engine normalizes CJK half-width punctuation in the output (`,;:?!` → full-width) —
Marian small models systematically emit half-width punctuation, a model-output characteristic. Three exception classes keep half-width:
digits flanked by digits (thousands separators `3,000`, times `12:30` — misconversion would be a semantic error); periods
(`.` → `。` risks damaging decimals/abbreviations; the model already emits full-width at sentence ends); and colons/question marks inside
URLs/code snippets, which cannot be distinguished from punctuation roles and may be converted to full-width when translating into CJK targets
(source text containing URLs/code should be manually checked after translation). Processing happens in the engine layer
(`src/engine/onnx_translate.rs`); the E2E golden output is the same translation as what ships.
Missing-model error example (bundle missing, at startup):

```text
Error: [translation] pairs[0] (en-zh) 加载失败: No encoder model found in
translation bundle models/opus-mt-en-zh; tried: …/onnx/encoder_model.onnx,
…/onnx/encoder_model_quantized.onnx
```

**Translation output post-processing and timeout**: translation applies deterministic post-processing at the engine exit (shared by the service layer and library users) — for `target=zh`, Traditional→Simplified normalization and repair of URL protocol separators and LaTeX escape symbols; model-level high-frequency mistranslations are repaired via the literal replacement table `[[translation.pairs.output_fixes]]` (in declaration order), see the `[translation]` section of [`config/config.toml`](../../config/config.toml). The HTTP global request timeout is configured via `[server] request_timeout_seconds` (CPU seq2seq translation of paper-length abstracts takes 15-130+s; `config/config.toml` sets it to 300s explicitly).

### Translation bundle contract

Directory structure (`model_path` points to the bundle root):

```text
<bundle>/tokenizer.json                        # required: tokenizers 0.23 only supports
                                               # the four tokenizer.json model types (.spm unsupported)
<bundle>/generation_config.json                # decoding anchors (decoder_start/eos token)
<bundle>/onnx/encoder_model.onnx               # fp32 (probe priority) or _quantized variant
<bundle>/onnx/decoder_model_merged.onnx        # merged variant (required for autoregression)
```

Recommended repos (HF, Xenova conversions): `Xenova/opus-mt-en-zh`,
`Xenova/opus-mt-en-es`. Download method (library API, the same `download_files` channel as the Laya bundle, HF direct only):

```rust
use vecboost::utils::hf_hub::{TRANSLATE_BUNDLE_FILES, TRANSLATE_BUNDLE_REPO, download_files};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let manifest: Vec<(String, std::path::PathBuf)> = TRANSLATE_BUNDLE_FILES
        .iter()
        .map(|f| ((*f).to_string(), std::path::PathBuf::from(f)))
        .collect();
    let downloaded = download_files(
        TRANSLATE_BUNDLE_REPO,
        &manifest,
        std::path::Path::new("models/opus-mt-en-zh"),
    )
    .await?;
    println!("downloaded {} files", downloaded.len());
    Ok(())
}
```

The built-in manifest constant `TRANSLATE_BUNDLE_REPO = "Xenova/opus-mt-en-zh"` has 7 files
(config.json, generation_config.json, tokenizer.json, and the fp32 and quantized variants of encoder and
decoder_model_merged under onnx/); consistency with the upstream files is pinned by an online integration test.

- `model_sha256` validates only the probe-matched encoder/decoder main models (either mismatching rejects); tokenizer.json and generation_config.json treat the bundle directory permissions as the trust boundary (same basis as the decision bundle).
- Capacity and memory: each bundle is about 559 MB on disk (fp32 dual models + int8 variant + tokenizer);
  residency accounting estimates disk × conservative factor 2.0 (the int8 residency factor has no measured calibration; correct after measurement);
  the pair cap of 16 is a memory-budget defense.

**Limitations and caveats**:

- Marian (2019 architecture) quality ceiling; no BLEU metric promised.
- **Same-pair serialization and backpressure** (review RES-1/PERF-1): inference per language pair is strictly serial
  (permits=1 semaphore); when more than 1 concurrent request hits the same pair, it immediately returns `503`
  Overloaded (no unbounded queueing) — clients should merge/backoff per pair;
  different pairs may run in parallel.
- `is_reliable` short-text boundary: whatlang deems too-short/digits-only/symbols-only text unreliable,
  and the auto-detection path returns an explicit 400 (`translate-detect-failed`); such requests should pass
  `source_language` explicitly. The language allowlist (`/detect`'s `allow` and
  `translation.pairs[].source_language`) only accepts language codes published by the detection engine
  (real ISO 639-1 codes like "sw"/"yo" are not among whatlang's 70 variants and are rejected loudly at config/request time).
- `task = "translate"` main-model usage always uses the default 512/512 token parameters (no configuration
  entry); translation deployments needing tunable parameters should use `[translation].pairs` (review SEC-5).
- Greedy decoding runs the no-cache branch (the Xenova merged-graph cache branch has an export defect; full
  recompute per step, O(L²) bounded by `max_new_tokens`) — a correctness-first trade-off; see
  the `src/engine/onnx_translate.rs` module docs.
- CJK characters mixed into English source text produce mojibake (OOV artifacts) in latin-vocab pairs such as en-es;
  CJK content should go through en-zh-class pairs.

**Limitations and caveats**:

- Weights are stored as F16 and upcast to F32 uniformly at load; `[model] device` follows
  candle conventions (CUDA/Metal used when available, AMD/OpenCL falls back to CPU loudly); there is no ort-style
  CUDA EP execution-provider switching.
- Temperature calibration keeps the status quo of "missing `laya_config.json` in the checkpoint directory falls back to 1.2";
  the bucket key format of `rl_agent_config.json` (e.g. `choice:3-5`) differs from the bundle calibration table's
  integer-cardinality keys and is currently not parsed. Deployments needing calibrated probabilities should use the onnx
  bundle path (the bundle ships the calibration file).
- The budget/validation surface is identical to the onnx path: head+options ≤192 tokens (default basis),
  state ≤256 tokens, over-budget 400; `model_sha256` validates only the main weight file.
- **Concurrency memory profile**: the decision forward materializes `[B, H, T, T]` attention-score tensors layer by layer
  (B = questions in batch, H = attention heads, T = sequence length), with transient memory O(B·H·T²); the decision
  forward has no internal serialization — K concurrent requests linearly amplify the transient peak (the onnx path is naturally serialized by the ort
  session mutex; the candle path has no such constraint). Size capacity by "peak concurrency ×
  per-request peak".
- **`memory_limit` accounting on the F32-residency basis**: candle decision weights are stored F16 on disk
  (≈0.84 GB) and upcast to F32 residency (≈1.7 GB) after load; the decision + candle combination
  is accounted at 2× disk size to align residency (F32 checkpoint disk assets are overestimated,
  the conservative direction); the gguf dequantization path (embedding task) still accounts at disk size, with higher
  actual residency — deployment must reserve headroom itself.
- The cross-check assertion `|Δlogit| ≤ 1e-4` is a hard gate (`tests/candle_decision_parity.rs`,
  run with a `--features onnx` build); drift in either the checkpoint or the onnx bundle goes red first.

#### Multiple checkpoint configuration and switching

The `[model.checkpoints.<name>]` preset table gives multi-checkpoint deployments named configurations: each
entry is a checkpoint preset that `POST /api/v1/model/switch` can switch to by name
(the three-checkpoint ecosystem: laya / laya-multilingual / laya-typed-decisions):

```toml
[model]
model_repo = "BAAI/bge-m3"        # main model (loaded at startup); checkpoints do not change startup behavior

[model.checkpoints.laya]           # table key = preset name (must match the entry's name; drift errors at startup)
name = "laya"
model_path = "models/laya"         # required
task = "decision"                  # required: embedding | decision
# optional below:
# engine_type = "onnx"             # defaults to inheriting the currently loaded model (i.e. [model].engine_type at startup; "candle"/"onnx")
# tokenizer_path = "models/laya/tokenizer/tokenizer.json"
# head_max_len = 192               # head+options token budget (default 192, English basis)
# max_len = 256                    # state truncation cap (default 256); must be configured pairwise with head_max_len
```

**Built-in `laya-multilingual` preset** (switchable with no configuration at all):
`task = "decision"`, `model_path = "models/laya-multilingual"`,
`head_max_len = 256`, `max_len = 256` (the multilingual checkpoint basis). Put
the bundle under `models/laya-multilingual/` and switch directly to get the right sequence budget;
when the preset table contains a same-name entry, the built-in is overridden **field-by-field** — fields you wrote win, and unwritten
optional fields (engine_type/tokenizer_path/head_max_len/max_len) inherit the built-in values
(e.g. customizing only `model_path` keeps the built-in 256/256 multilingual budget).

**Relationship with switch_model**: when a switch request's `model_name` matches a preset name (including built-ins),
the preset's `model_path`/`task`/`engine_type`/`tokenizer_path` apply as the **default layer**
— explicit request fields still win; a switch that misses all preset names behaves exactly as without a preset table.
A hit activates that checkpoint's sequence budget: the error message for over-budget requests carries the effective
`head_max_len` value, which can confirm the switch succeeded.

**fail-fast semantics**: unknown fields, missing required fields (name/model_path/task),
invalid task/engine_type values, zero or over-hard-cap parameters (a single field over 8192, or
head_max_len + max_len + 4 fixed special tokens exceeding the window), and table keys not matching the entry's name
all **error loudly at startup**, refusing startup with no silent clamping or ignoring.
Writing only one of `head_max_len`/`max_len` also errors at startup — same semantics for
same-name entries under the built-in `laya-multilingual` (field-level inheritance only applies to pair-wise defaults; it will not
stitch your one-sided value with the built-in value into a valid pair).

### Transcription service configuration

The `[transcribe]` section assembles the Qwen3-ASR transcription service (`transcribe` feature; the endpoint
`POST /api/v1/transcribe` and gRPC `vecboost.transcribe` are always registered):

```toml
[transcribe]
enabled = false                  # default false: requests get 400 transcribe-not-configured when disabled
models_dir = "models/qwen3-asr"  # bundle root with the three graphs + silero_vad.onnx + tokenizer/
vad_threshold = 0.5              # silero VAD probability threshold
intra_threads = 0                # session intra-thread count (0 = available_parallelism)
no_spin = false                  # ORT spin control
cuda = false                     # CUDA EP (requires an onnxruntime shared library with CUDA)
```

- With `enabled=true`, assembly happens eagerly at startup; a missing bundle **fails fast** (same basis as `[translation]` pairs).
- The input contract is 16kHz mono f32 samples (≤2h); WAV decoding is the client's responsibility, with the call order read wav → samples → this endpoint (the local thin-shell CLI follows exactly this order; that directory is not committed).
- Long audio is VAD-segmented and decoded segment by segment inside the service; fully silent input returns empty `segments`/`text` (an explicit empty response).

#### Input character defense

Text inputs to embedding and decision inference run a unified control-character validation; a hit returns 400 `ValidationError`:

| Character class | Handling | Notes |
|----------|------|------|
| NUL / C0 control characters (U+0000–U+001F except `\t` `\n` `\r`) | **Reject** | Injection surface and downstream tokenizer protection |
| C1 control characters (including U+0085 NEL) | **Reject** | Same as above |
| U+2028 / U+2029 (LINE/PARAGRAPH SEPARATOR) | **Reject** | Some log viewers/terminals render line breaks at these — a rendering-level log-obfuscation surface, on par with `\n` |
| `\t` `\n` `\r` | Exempt | Normal text formatting characters |

> **⚠️ Compatibility note**: rejecting U+2028/U+2029 tightens the input surface — line/paragraph separators occasionally seen in web-scraped text and JS
> source previously passed `/v1/embeddings` and now return 400. Clean existing data of these two classes before ingestion (the validation also applies to decision-request name/options/state
> string leaves).

> **Parsing basis note**: JSON deserialization of the decision request body (`DecisionRequest`/`DecisionQuestion`) does **not** enable
> `deny_unknown_fields` — unknown/misspelled keys (such as a misspelled `instructions`) are silently ignored, and fields pass validation in their default form (empty string)
> into downstream processing. This is a forward-compatibility trade-off on the API request surface, different from the explicit-failure basis of the config-side engine-level `ModelConfig`;
> clients should verify request field names against the OpenAPI schema.

Undetectable (no detection signal / digits-only / symbols-only) returns **200** + `language: null` +
`is_reliable: false` (explicitly expressed, never a fabricated language); the `allow` field accepts a language-code allowlist to narrow candidates (invalid codes 400). The language-code contract (lowercase ISO 639-1 first, 639-3 where no equivalent)
and all error semantics are in [API Reference · Language detection](API_REFERENCE.md#language-detection-detect).

> **The `task` field (landed)**: switch requests may carry an optional `task` field (`embedding` /
> `decision` / `translate` / `transcribe`) to switch the task dimension at runtime; the fallback chain is **request value first → inherit the current model →
> fall back to `embedding` when no current model**. With `task = "decision"`, the EngineFactory's
> task dispatch arm loads the decision pipeline (a missing/incomplete bundle reports `ModelLoadError`);
> after a successful switch, the rerank and decision services swap their underlying engines in sync (switch propagation); request bodies without
> the `task` field behave unchanged (`#[serde(default)]` zero breakage).
>
> **`[model.checkpoints]` preset coupling**: when `model_name` matches a preset name (including the built-in
> `laya-multilingual`), the preset's `model_path`/`task`/`tokenizer_path`/
> sequence budget apply as the default layer (explicit request fields still win); see "Configuration → Multiple
> checkpoint configuration and switching".

```bash
curl -X POST http://localhost:9002/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{
    "username": "admin",
    "password": "Secure@Passw0rd!2026"
  }'
```

**Response:**

```json
{
  "token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 86400
}
```

> **💡 Note**: `expires_in` is the server-returned number of **seconds** until token expiry (not 0; default `[auth] token_expiration_hours = 24` → 86400s, overridable via `token_expiration_seconds`). The server validates expiry against it and clients may cache it for expiry hints — do not treat `0` as a special "server-managed" signal.

---

### Using the token

Include the token in API requests:

```bash
curl -X POST http://localhost:9002/api/v1/embed \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIs..." \
  -d '{"text": "Hello, world!"}'
```

---

### Token expiry

The server returns the seconds until expiry in the login response's `expires_in` (default 86400s). Adjust the lifetime (hours) in the config file:

```toml
[auth]
token_expiration_hours = 24
```

## 🌍 Internationalization (i18n)

VecBoost supports bilingual (English/Chinese) error responses, automatically negotiating language via the `Accept-Language` request header.

### Language priority

1. **Request level**: the `Accept-Language` header (e.g. `Accept-Language: zh-CN,zh;q=0.9`)
2. **Global default**: the `VECBOOST_LANG` environment variable (e.g. `VECBOOST_LANG=zh`)
3. **System locale**: the `LC_ALL`/`LANG` environment variables
4. **Fallback**: English (`en`)

### Example

```bash
# Chinese error response
curl -X POST http://localhost:9002/api/v1/embed \
  -H "Content-Type: application/json" \
  -H "Accept-Language: zh-CN" \
  -d '{"text": ""}'

# Response (Chinese)
{"error": "文本不能为空", "code": 400, "error_code": "error-invalid-input"}

# English error response (default)
curl -X POST http://localhost:9002/api/v1/embed \
  -H "Content-Type: application/json" \
  -d '{"text": ""}'

# Response (English)
{"error": "Text cannot be empty", "code": 400, "error_code": "error-invalid-input"}
```

> **💡 Note**: i18n covers all user-visible messages: HTTP JSON error responses, CLI help text, gRPC error details, and startup error logs. Translation keys are defined in `src/i18n/locales/{en,zh}/messages.ftl` and `errors.ftl` (632 keys per language: `messages.ftl` 612 + `errors.ftl` 20).

### Multi-replica shared state (Redis)

With the `distributed-redis` feature, rate limiting and the exact vector cache can be externalized to Redis:

```toml
[rate_limit]
backend = "redis"
redis_url = "redis://127.0.0.1:6379"
global_window_ms = 60000

[embedding]
cache_backend = "redis"
redis_url = "redis://127.0.0.1:6379"
```

| State surface | memory (default) | redis |
|--------|----------------|-------|
| Rate limiting (global / IP / User / ApiKey) | In-process | Shared (Lua-atomic fixed window; per-key fixed 60s window) |
| Exact vector cache | In-process (WAL optional) | Shared (no WAL, bloom disabled, keys bound to the weight fingerprint) |
| Semantic-cache fuzzy hits | In-process | Redis-shared (`distributed-redis`; trigram index, no RediSearch needed) |
| Ban list | In-process | Redis-shared (`distributed-redis` + `ban-sync`) |

Build: `cargo build --features "db,sqlite,distributed-redis"` (or `db,postgres`). `cache_backend = "redis"` and `[embedding] persist_path` are mutually exclusive; if Redis initialization fails, the service refuses to start (no silent fallback to memory).

**TLS and escape hatch**: oxcache rejects all non-TLS (`redis://`) connections to prevent production misuse — set `OXCACHE_ALLOW_INSECURE_REDIS=I_UNDERSTAND_THE_RISKS` to bypass in development/loopback environments; production uses `rediss://` (TLS).

**Window semantics**: the per-key dimension uses a fixed 60s Lua fixed window, and `global_window_ms` applies only to the global dimension (shrinking it does not proportionally relax per-key quotas); a fixed window allows up to 2× quota bursts at window boundaries, and rejected requests are counted too. Redis rate-limit checks are fail-closed: a single Lua round trip exceeding 500ms without response rejects the request (a half-dead Redis never hangs request threads).

## 🔧 Troubleshooting

### Common issues

#### Service fails to start

**Problem**: the service fails to start due to a configuration error.

```bash
# Check the logs
./target/release/vecboost 2>&1 | head -50
```

**Common causes and solutions:**

| Problem | Solution |
|------|----------|
| JWT secret too short | Ensure `jwt_secret` is at least 32 characters |
| Port already in use | Check the port: `lsof -i :9002` |
| Model download failed | Verify network connectivity |

---

#### GPU not detected

**Problem**: GPU acceleration is not working.

```bash
# Check GPU availability
nvidia-smi

# Verify the CUDA installation
nvcc --version

# Check application logs
grep -i cuda target/release/vecboost.log
```

**Solutions:**

1. Install the CUDA toolkit
2. Rebuild with `--features cuda`
3. Verify the GPU driver is up to date

---

#### Out of memory

**Problem**: the service crashes with OOM.

**Solutions:**

1. Reduce `batch_size` in the configuration
2. Limit `cache_size`
3. Enable CPU fallback: `gpu_oom_fallback_enabled = true`
4. Increase the container memory limit

---

#### Authentication failure

**Problem**: 401 Unauthorized error.

```bash
# Check whether the token is valid (verify current user info via /auth/me)
curl http://localhost:9002/api/v1/auth/me \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIs..."
```

**Solutions:**

1. Refresh the token via the login endpoint
2. Check system clock synchronization
3. Verify whether the JWT secret changed

---

#### Rate limiting / overload

**Problem**: rate limiting triggered — the auth rate-limit middleware (per IP/user/API key) returns `429` (with `Retry-After`); application-level token-bucket rate limiting (`error-rate-limit`) and a full priority queue (`error-overloaded`) return `503`.

**Solutions:**

1. Implement exponential-backoff retries (read `Retry-After` on 429; back off on 503 too)
2. Adjust tier thresholds in `[rate_limit]` (global / ip / user / api_key `*_requests_per_minute`)
3. Add IPs to the whitelist

```toml
[rate_limit]
ip_whitelist = ["127.0.0.1", "10.0.0.0/8"]
```

## ❓ FAQ

**Q: Can I use my own model?**

A: Yes — set `model_repo` to a HuggingFace model ID or a local path.

---

**Q: How do I change the model at runtime?**

A: Use the `POST /api/v1/model/switch` endpoint.

---

**Q: What is the maximum batch size?**

A: Configurable via `batch_size`, default 32. Larger values increase throughput but use more memory.

---

**Q: Does VecBoost support streaming?**

A: Not currently; planned for a future release.

---

**Q: How do I upgrade to a new version?**

A: Stop the service, build/pull the new version, update the configuration if needed, and restart.

---

**Q: Can I run multiple instances?**

A: Yes — configure a load balancer with session affinity to handle authenticated requests.
